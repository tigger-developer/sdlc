#+SCHEMA: 8

* Emergency authority and scope
- Authority :: Approved 2026-09-28 through =BYPASS-GATE-7=; the bounded temporary
  specification is reconciled here after implementation, without advance gate claims.
- Outcome :: *Reset invalidates the selected audit regardless of recorded status*.
  Prior invocations lose write authority; unrelated audits continue.
- Scope :: Audit record persistence, reset, recovery coordination, local tests and documentation.
- Exclusions :: No provider termination, global process searches, installation,
  other-project changes or permission changes. Filesystem and invalid-input errors
  remain errors; reset does not manufacture a missing record.
- Baseline :: [[file:../W019-automatic-audit-recovery/spec.org][W019 - Automatic audit recovery]],
  [[file:../../docs/ARCHITECTURE.md][Audit architecture]], =reset_test.go= and
  =verdict_budget_test.go=. The old running-refusal test is superseded by AC020.1.

* Acceptance criteria
** AC020.1 - Reset every recorded status :ac:
:PROPERTIES:
:CUSTOM_ID: ac020-1
:END:
Authorized =--reset= accepts running records with or without a session identity,
clears the selected allowance and lockout, retires context and preserves history
and findings. Repetition before another attempt is a no-op. Missing or malformed
records and invalid invocation still fail explicitly.
- Proven by :: [[#rt020-1][RT020.1 - Reset and stale writers]].

** AC020.2 - Old runs cannot undo reset :ac:
:PROPERTIES:
:CUSTOM_ID: ac020-2
:END:
After reset, an earlier invocation cannot persist identity, failure or verdict,
overwrite a new attempt, or adopt the new generation for provider retries.
A new normal invocation can start from the reset context. No process detection
or termination is required; an old provider request may finish without a verdict.
- Proven by :: [[#rt020-1][RT020.1 - Reset and stale writers]].

** AC020.3 - Serialize record updates and isolate projects :ac:
:PROPERTIES:
:CUSTOM_ID: ac020-3
:END:
Generation comparison and writes form one short process-safe transaction.
Concurrent updates to distinct entries in one record preserve all entries.
Resolved aliases share protection. Another project's record remains unchanged
and writable. Provider execution never holds the record lock.
- Proven by :: [[#rt020-2][RT020.2 - Concurrent record persistence]].

* Solution design
- State :: Optional unsigned =generation= on each context; missing means zero.
  Reset increments it, clears identity and current verdict, appends the existing
  selected-gate budget boundary and preserves findings/history. A subsequent
  empty reset is a no-op. Counter overflow is an explicit failure.
- Persistence :: The existing YAML writer remains the sole checkpoint path.
  Every normal update compares generations under a record-file lock. Reset and
  legacy migration use the same lock. Atomic replacement preserves reader consistency.
- Lock :: Existing Unix =flock= mechanism, already used by cooldown storage.
  Resolved file/parent paths identify a persistent lock in a private, self-ignored
  sibling =.audit-locks/= directory. No provider execution or process search occurs
  under the lock; close or process exit releases it.
- Recovery :: Obsolete writes return a distinct error. Retry coordination stops
  before handling it as a provider incident; rereading after a provider failure
  checks generation before adopting the saved state.
- Compatibility :: Test-code and delivery-code still share implementation context;
  resetting either retires that context while preserving the other's counters.
  Older running binaries do not implement fencing and must exit before concurrent
  use of the upgraded tool. Local macOS and Linux retain the existing Unix boundary.
- Security :: No new dependencies, external calls, process signals or widened
  access. Locks use 0600 files, 0700 directories and no-follow opens. History and
  logs remain retained; generation does not authenticate untrusted manual writers.
- Verification :: RTs cover persistence outcomes; OT reviews lock lifetime and
  recovery control flow. Existing regression pack covers provider and gate contracts.
