#+TITLE: W021 - Warn before reviewing frozen audit inputs
#+SCHEMA: 8
#+STARTUP: overview
#+OPTIONS: toc:2 num:nil

* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:
** Outcome
- Calling agents *see readiness and input-freeze obligations* in help and at startup.
** Before
- Startup *reported liveness only*; help omitted explicit mutation consequences.
** After
- Each provider start *warns before liveness*; periodic heartbeats stay brief.
** Changes
- Help and startup *require finished, passing delivery checks* and settled evidence.
** Unchanged
- *Gate prerequisites and mutation detection remain unchanged*; no new watcher.
** Edge cases
- *Capped private logs still permit the warning*; private identities stay hidden.
- *Later edits invalidate applicability*, not the historical evidence for old bytes.
** Decisions
- *Embed reviewable notice text* in the existing diagnostic output path.
** Next step
- *Review the warning and verification evidence* for release and operator closure.

* Acceptance Criteria
** AC021.1 - Explain readiness and audit applicability :ac:
:PROPERTIES:
:CUSTOM_ID: ac021-1
:END:
Help and startup explain that *delivery-code waits for written code, tests and
documentation*, finished passing automated/one-off checks, and settled GREEN
RT/OT records. Any change to reviewed code, tests, documents or validation during
or after review *invalidates the audit for the changed candidate*. Affected
checks and review must be repeated. Warnings distinguish invalidation from
*detection after provider execution*, without claiming immediate cancellation.
Definition/test-code prerequisites and outstanding AMBER UTs remain unchanged.
- Proven by :: [[#ot021-1][OT021.1 - Review packaged warning and documentation]].

** AC021.2 - Show reminder at startup without noisy heartbeats :ac:
:PROPERTIES:
:CUSTOM_ID: ac021-2
:END:
Every provider start *emits the warning on stderr before liveness*, including
when the private log is capped. Periodic heartbeats do not repeat it. No private
identity is exposed; stdout retains its result/readiness contract.
- Proven by :: [[#rt021-1][RT021.1 - Startup warning and capped diagnostics]],
  [[#ot021-1][OT021.1 - Review packaged warning and documentation]].

* Edge Cases
- *Provider recovery repeats the startup reminder* because each launch emits the
  existing start event; it introduces no new retry or process behaviour.
- *A capped log does not suppress caller output*, covered by RT021.1 - Startup
  warning and capped diagnostics. Output write errors remain propagated.

* Solution Design
- Reuse :: Add the *embedded Markdown notice* to the existing locked diagnostic
  writer's start-event branch. Keep heartbeat output and private log bounds intact.
- State :: No persisted schema or configuration changes. No new dependencies.
- Scope of validity :: The warning applies to the reviewed candidate. Unrelated
  changes do not invalidate it; old verdicts retain their historical meaning.
- Security :: *No new access or provider calls*. Static public notice text never
  includes private identities. Existing writer mutex and error propagation remain.
- Architecture :: Existing output boundary; no structural architecture change.
