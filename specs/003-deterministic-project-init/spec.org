* Specification Summary
:PROPERTIES:
:CUSTOM_ID: summary
:END:

- Outcome :: =sdlc-init= *preselects project technologies deterministically*,
  *inherits global settings silently*, and supports a *model-free migration*.
- Before :: Technology selection launched a model, and every global default was
  presented again as a project question.
- After :: YAML heuristics propose technologies for operator confirmation;
  populated global defaults are skipped unless explicitly reopened.
- Changes :: Add schema-owned technology detection, a Lua standard,
  =--override-global-config=, and =--no-agent-scan=.
- Unchanged :: The operator confirms project technologies, project-owned facts
  remain project questions, and archived v2 classification still uses a model
  unless explicitly skipped.
- Edge cases :: Blank repositories have no recommendation; archives and generated
  dependencies do not influence selection; Hugo implies the web standard.
- Decisions :: Heuristics optimize useful preselection, not perfect inference.
- Next step :: Run the implementation gate, then let the operator test the
  installed initializer.

The summary above accurately and completely represents the detail below.

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem

The initializer used a fresh model context to infer a small, bounded list of
technologies from familiar repository files. This added cost and latency before
an operator-confirmed question. It also repeatedly asked about settings already
defined as global defaults.

** Outcome

Project initialization remains operator-controlled while routine detection and
global inheritance become fast, deterministic, and schema-driven.

** Scope

*** In scope

- Technology recommendations from maintained project files.
- Lua engineering guidance and Lua source detection.
- Silent inheritance of populated global defaults.
- Explicit reopening of global-default questions.
- Optional model-free preservation of archived Spec Kit work.

*** Out of scope

- Perfect technology inference.
- Semantic classification of product or architecture authorities.
- Automatic selection without operator confirmation.

*** Unchanged

- Product kind, technology selection, authorities, and infrastructure role are
  project facts and cannot be supplied by global configuration.
- Existing deterministic authority discovery and migration behaviour remains.

** Authority and starting point

- Project profile :: [[file:../../.sdlc/project.yaml][=.sdlc/project.yaml=]]
- Product authority :: [[file:../../README.md][=README.md=]]
- Architecture authority :: [[file:../../docs/ARCHITECTURE.md][=docs/ARCHITECTURE.md=]]
- Configuration schema :: [[file:../../src/config/project-init.schema.yaml][=src/config/project-init.schema.yaml=]]

** Constraints and dependencies

- Detection uses the bounded Git file inventory already used by initialization.
- The schema remains the canonical source for signals and implications.
- No model or metered service participates in technology detection.

** Decisions

- False positives or omissions are acceptable because recommendations are
  visibly preselected and require operator confirmation.
- Lua is preferred to shell where a host supplies Lua or scripting logic needs
  real data structures and modules; a standalone runtime still requires
  justification.

** Unresolved blockers

- None.

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context

- Relevant components :: The YAML schema defines inputs; the Go initializer
  interprets them; the existing multi-select obtains operator confirmation.
- Ownership boundary :: The SDLC owns recommendations and prompts; the operator
  owns final project classification.
- Existing pattern :: Reuse the bounded Git inventory and schema-driven UI.

** High-level design

*** Flow

1. Load and validate installed technology standards and detector rules.
2. Match maintained file basenames and extensions, excluding declared paths.
3. Add declared implications, render evidence, and pass recommendations to the
   existing confirmation control.
4. During configuration resolution, silently inherit populated global values
   unless override mode explicitly reopens them.

*** Interfaces and configuration

- Interface :: =technology_detection= in =project-init.schema.yaml= owns
  exclusions, basenames, extensions, and implications.
- Interface :: =sdlc-init --override-global-config= reopens global questions.
- Interface :: =sdlc-init --no-agent-scan= preserves archived v2 work as
  unresolved =REVIEW= items.
- Compatibility :: Existing CLI, environment, project, global, and default
  precedence remains unchanged.

*** Data and state

- Inherited global values remain absent from =.sdlc/project.yaml=.
- Technology recommendations are transient and are persisted only after
  operator confirmation.

*** Failure behaviour

- Invalid or incomplete detector schemas fail validation.
- An unavailable Git inventory emits a warning and falls back to manual
  technology selection.

** Architecture impact

*** Security impact

- Threat boundary :: Detection reads only the bounded repository file list and
  no longer sends project structure to an external model.
- Data and secrets :: File contents and =.env= files are not read.
- Access :: No additional authority is introduced.
- Conclusion :: The change reduces external disclosure and model execution.

*** Other relevant qualities

- Reliability :: Deterministic rules make repeated recommendations stable.
- Performance :: Removes one model startup from routine initialization.
- Operability :: New switches are exposed through command help.
- Accessibility :: Existing selectable, confirmable question layout remains.
- Portability :: Detection is filesystem- and Git-based, without a model
  provider dependency.
- Maintainability :: New technologies add their standard and detector rule in
  the same schema-controlled release.
