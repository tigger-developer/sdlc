This is the canonical SDLC v3 specification template.
The SCHEMA value is this template's version, not the SDLC release or an audit
result. Copy it unchanged into new specifications; follow ISSUES.md for versioning.

Use a new project-wide work number and never reuse an identifier. Replace every
instructional placeholder before definition sign-off. The document title must
name the change as =WNNN - [concise change-specific title]=. Generic titles such
as =Spec sheet=, =Specification=, =Change=, or =Untitled= are invalid.
Keep the opening section named =Synopsis=; do not repeat the document title
as its headline. Preserve its =CUSTOM_ID: summary= for stable links.

Apply the ABC presentation contract in =ISSUES.md=. Retain the core level-one
sections. Use level-two Synopsis categories with short bullets, level-two
records elsewhere, and deeper headings only for genuine children. Subordinate
design/quality sections are optional when irrelevant; security impact is always
required. Use description lists for labelled facts, not paragraphs disguised
as list items. Do not simulate headings with bold labels.

Keep the document concise, but sufficient for a new agent to deliver without
the drafting conversation. Within substantive text, use native Org emphasis to
bold the smallest functional words or phrases that carry the distinctive state,
action, qualifier, quantity, boundary, or outcome. Read in order, those bold
fragments alone must communicate the statement's functional meaning. Include
enough of the subject or context to make that bold-only reading understandable;
a headline or preceding line does not replace it. Do not bold headlines,
labels, identifiers, structural words, whole sentences, or every occurrence of
a term. Use the smallest sufficient set of fragments; if most of a sentence is
bold, reduce it until the emphasis is selective again.

Illustrative report example only; do not copy these requirements into a project:

Synopsis / After:
- The *archive* keeps *one report* for each *execution*.
- *Retries* do not create *duplicates*.

Acceptance criterion:
- Criterion :: Given a repeated execution identifier, the *archive* contains
  *one report* for that *execution*.

Test definition:
- Setup :: An execution already has an archived report.
- Action :: *Retry* that execution.
- Expected :: The *archive* still contains *one report* for the execution.

Give each detailed fact one home: ACs own outcomes, design owns exact after-state
contracts, tests own actions and observable expectations, and handoff owns entry
conditions and required reading. Link between them; do not copy entire contracts.
The Synopsis and explicit test expectations are intentional repetitions. Preserve
material detail without imposing a word limit or creating a second summary file.

The work item's TODO keyword in =docs/work.org= is its sole lifecycle state.
Only the harness creates or updates =audits.yaml=; read the current gate there.
Do not copy audit findings, verdicts or session state into this specification.
Follow annotation review in =ISSUES.md=: preserve resolved feedback and its
disposition in =feedback.yaml= before removing its annotation. Unresolved feedback
stays visible; no annotation records or blocks, even resolved or empty ones, may
remain at definition audit or sign-off. Use the annotation tool's documented
semantics, not guessed syntax. Ordinary authoring comments are not annotations.
Only explicit operator sign-off may replace =OPERATOR_SIGNOFF= with the authority,
date and approval scope. Design approval does not override an implementation hold.
A material specification change requires renewed operator approval and current
audit evidence: reset operator sign-off to PENDING and move the work item to
REVIEW, preserving history. Never edit the audit record directly.
#+end_comment

* Test Definitions
:PROPERTIES:
:CUSTOM_ID: test-definitions
:END:

#+begin_comment
Use the test classifications and automated TDD rule resurrected from SDLC v1.
Classify each test honestly:

- RT is a persistent automated regression test included in the normal suite.
- UT is a human user test whose result is recorded, with no artificial test file.
- OT is a bounded one-off check that is not retained in the regression suite.

Automated RTs follow TDD and must fail for the expected reason before
implementation. A test must earn its place, exercise the relevant boundary, and
be defined well enough to reproduce. Do not simulate an undocumented third-party
system or use source-text greps as behavioural evidence.

For a dense case group, keep one test ID and shared setup/boundary. Use named
level-three cases or a compact case/outcome table rather than long Action and
Expected paragraphs. Preserve explicit observable outcomes and AC mappings;
"see design" alone is not a test. Do not create more IDs or a new harness just
to reformat cases. Optional table layout:

| Case | Action or input | Observable expected result | AC |
|------+-----------------+----------------------------+----|
| [Descriptive case] | [Bounded action] | [Concrete outcome] | [AC link] |
#+end_comment
