This is the project's canonical work and requirements index. Each fact has one
authoritative representation:

- *Current lifecycle state* :: The TODO keyword on the work-item headline.
- *Classification* :: One or more tags on that headline.
- *Stable metadata* :: The work item's property drawer.
- *Current definition* :: The linked =spec.org= file.
- *Evidence* :: The linked =audits.org= and =validation.org= files.
- *History* :: Git history and explicitly linked archived sources.

Do not repeat lifecycle state in a property, section, specification, or evidence
file. Work items remain under one heading when their state changes. Use one
monotonically increasing project-wide work number and never reuse an identifier,
including after abandonment, deletion, retirement, or archival.

* Ledger vocabulary

:VISIBILITY: folded

The file directives declare the permitted TODO states and standard tags. This
section defines their meanings.

** Lifecycle states

- =TODO= :: Defined but not started.
- =ACTIVE= :: Delivery is underway.
- =BLOCKED= :: Delivery cannot continue because of a named external dependency.
- =REVIEW= :: Human review, validation, or disposition is required.
- =DONE= :: Delivered, verified, and closed.
- =ABANDONED= :: Deliberately not delivered. Its identifiers remain reserved.

** Legacy requirement states

- =PENDING= :: The requirement or some required evidence remains unverified.
- =FAILING= :: Current evidence shows that the requirement does not hold.
- =SUPERSEDED= :: A named later requirement replaces or retires it.
- =HOLD= :: The requirement remains current and its recorded evidence passes.
- =ASSUMED_PASS= :: Migration inferred delivery under a recorded heuristic; it
  is not a contemporaneous test result.

** Standard tags

- =feature= :: New or changed product behaviour.
- =defect= :: Incorrect existing behaviour.
- =maintenance= :: Internal upkeep without intended product-behaviour change.
- =migration= :: Historical or framework migration work.
- =legacy= :: Material governed by an earlier delivery process. Apply it to the
  parent headline so the whole subtree inherits the classification.

Tags are non-exclusive classifications. Add a project-specific tag only when it
provides a durable cross-cutting category that the standard tags cannot express.

** REVIEW W014 - Recover replaced installer artefacts through Trash :maintenance:
:PROPERTIES:
:CUSTOM_ID: w-014
:SOURCE: operator BYPASS-GATE-7
:CREATED: 2026-09-13
:END:

- Authority :: Operator requests Trash for replaced managed artefacts, adjacent
  backups only for configuration, and no separate spec sheet for this emergency.
- Scope :: SDLC installer and companion personal-agent deployer. No deployment,
  existing-backup cleanup or change to initializer migration archives.
- AC014.1 :: Replaced owned files, directories and links remain *recoverable in
  Trash*, without new adjacent backups. Symlink targets and unrelated entries
  remain untouched. Proven by RT014.1, managed-replacement and full installer tests.
- AC014.2 :: A missing or failed *trash* command, or a successful command that
  leaves its input present, *stops replacement*. Proven by RT014.2 in both installers.
- AC014.3 :: Merged *configuration retains an exact adjacent backup* before its
  update; existing recovery paths remain available. Proven by RT014.3 and the
  companion deployer's configuration-backup assertions.
- Design :: Reuse existing ownership/planning boundaries. One bounded, literal
  =trash ABSOLUTE_PATH= invocation handles each displaced managed path; inspect
  absence before replacement. Keep the configuration backup/restore path separate.
  Read source bytes before trashing the installed file. No new configuration knob.
- Security :: No elevated permissions or shell evaluation. Trash is a required
  trusted local executable; regression tests substitute a disposable recovery tree.
  Failure stops the batch but does not roll back prior successfully applied items.
- Test boundary :: RTs invoke actual installer logic/CLI against temporary trees;
  check new bytes, recoverable old bytes, failures, links and idempotence. No metered
  service or real host Trash is used. Native installation remains operator validation.
- Evidence :: [[file:../specs/W014-installer-trash/validation.org][W014 - Validation]];
  [[file:../specs/W014-installer-trash/audits.yaml][W014 - Harness-owned audit record]].

*** Emergency follow-up - Unusable audit result fallback

- Authority :: Operator explicitly extends BYPASS-GATE-7 to the audit harness
  after the configured primary reports its subscription limit. Confirmed usable
  verdicts are PASS, FAIL and PROVISIONAL PASS; running work is not a failed attempt.
- AC014.4 :: An *audit attempt ending without a usable verdict* selects the
  configured fallback *once*, retaining history and the shared round budget.
  Valid verdicts do not trigger it; later review resumes the selected fallback.
- AC014.5 :: *Local configuration, evidence-integrity and record failures* do
  not bypass their checks. Exhausted budgets do not launch another provider.
  Non-audit definition/build retain authentication-only fallback.
- RT014.4 :: Local executable provider doubles exercise usage-limit and launch
  failures, timeout, empty/malformed/wrong-gate responses, all valid verdicts,
  failed fallback, exhausted rounds, changed evidence and retained-session reuse.
  Observe actual calls, audit history, configured tuple and final output. Covers
  AC014.4 and AC014.5; no metered provider enters automated tests.
- Design :: Extend the existing recovery decision after provider termination
  and verdict validation. Typed provider incidents permit fallback; local evidence
  and record errors stop. No new configuration fields, provider-message catalogue,
  permission bypass, timeout increase or manual session replacement.
- RT014.5 :: A failed primary writes a plausible verdict to the temporary
  response file; the fallback exits without writing output. No stale verdict
  may be accepted. Clear the CLI-owned temporary response before every attempt.
  Covers AC014.4 and AC014.5.
- Security :: Exact evidence checks and configured permissions remain mandatory.
  Fallback is operator-configured; no unconfigured provider is chosen.
