# Handover

Use this skill only when the user invokes it.

Prepare a handover that lets a new agent resume the current work without relying on this conversation.

1. Establish the current working directory and project scope. Before writing, propose one expanded absolute path matching `[cwd]/[hyphen-delimited-task-descriptor]-[YYYY-MM-DD].md`, using the current date in ISO format. Ask the user to confirm that path or provide another permitted destination. Do not write until the user confirms. If the path exists, inspect it and ask before replacing or appending; preserve existing content.
2. Gather as much relevant detail as the current accessible context supports. Inspect current repository state and important source or evidence paths when needed to distinguish current observations from recollection. Do not claim to export hidden instructions, inaccessible earlier turns, private reasoning, or an exact transcript. Do not copy credentials, tokens, private keys, or unnecessary personal data. Identify any material detail omitted for that reason.
3. Before writing the note, inspect every authorized repository and branch on which the agent worked in this task. Commit all attributable outstanding work and push each worked branch to its configured remote. Verify the remote contains each pushed commit. Never stage another person's or unrelated changes, force a push, or bypass a failed check. If any work cannot be committed or pushed safely, stop and ask the user to resolve the blocker.
4. Write the handover note on the current project's `master` branch only. Confirm that `master` exists and can be used without disturbing other work. Do not create or commit the note on a feature branch or any other branch. If the confirmed destination cannot be committed on `master`, stop and ask the user for a compatible destination. Follow the governing project's write, documentation, and Git rules. The note must contain the task and intended outcome; project and working directory; governing instructions and workflow route; user decisions and exact constraints; verification performed with commands, results and limits; open questions, blockers and risks; and concrete next steps in order. Give each branch worked on its own clear account of work performed, files changed, relevant commits and revisions, current worktree state, remote destination, and verified push status. State explicitly which work is on `master` and which is on another branch; do not imply that unmerged branch work is on `master`. Include useful paths, identifiers with descriptors, and dates or revision references where they matter. Distinguish observed facts, user statements, decisions, hypotheses, and unverified recollection. Preserve important wording verbatim when its exact form matters and is available. Record any work that could not be pushed, with its branch and reason.
5. Commit the handover note on `master`, push `master`, and verify that the remote contains the note commit. A handover note is a record, not approval, validation, closure, or authority to perform further actions. Verify that the file contains the intended sections, then report its path, the branch and push results, and any material limitations. Do not claim all work is checked in and pushed unless verification supports it.
