# Handover

Use this skill only when the user invokes it. Prepare a handover that lets a new agent resume the current work without relying on this conversation.

1. Establish the current working directory and project scope. Before writing, propose one expanded absolute path matching `[cwd]/[hyphen-delimited-task-descriptor]-[YYYY-MM-DD].md`, using the current date in ISO format. Ask the user to confirm that path or provide another permitted destination. Do not write until the user confirms. If the path exists, inspect it and ask before replacing or appending; preserve existing content.
2. Gather as much relevant detail as the current accessible context supports. Inspect current repository state and important source or evidence paths when needed to distinguish current observations from recollection. Do not claim to export hidden instructions, inaccessible earlier turns, private reasoning, or an exact transcript. Do not copy credentials, tokens, private keys, or unnecessary personal data. Identify any material detail omitted for that reason.
3. Write a self-contained Markdown note with the task and intended outcome; project and working directory; governing instructions and workflow route; user decisions and exact constraints; work performed; files changed; current Git branch, revision and worktree state; verification performed with commands, results and limits; open questions, blockers and risks; and concrete next steps in order. Include useful paths, identifiers with descriptors, and dates or revision references where they matter. Distinguish observed facts, user statements, decisions, hypotheses, and unverified recollection. Preserve important wording verbatim when its exact form matters and is available.
4. Follow the governing project's write, documentation, and Git rules for the destination. Before handing over, inspect every authorized repository and branch on which the agent worked in this task. Commit all attributable outstanding work, including the handover note when it belongs in Git, then push every worked branch to its configured remote. Verify the remote contains each pushed commit. Never stage another person's or unrelated changes, force a push, or bypass a failed check. If any work cannot be committed or pushed safely, stop and ask the user to resolve the blocker; record the exact branch, work and reason in the note. Do not claim all work is checked in and pushed unless verification supports it.
5. A handover note is a record, not approval, validation, closure, or authority to perform further actions. Verify that the file exists and contains the intended sections, then report its path, the branch and push results, and any material limitations.
